# Changelog

## 1.6.4 — 2026-11-17 (слабые модели: ответ не по схеме больше не рушит конспект)

* **Чужой формат ответа приводится к схеме, а не отбрасывается.** Новый `src/ai/coerce.js` разворачивает обёртки `{"result": …}` / `{"summary": {…}}`, понимает `snake_case` и русские имена полей (`суть`, `ключевые тезисы`, `заголовок`), превращает строку с маркерами в список пунктов, читает таймкоды вида `[1:10]`, `at`, `ts`, `timestamp`, секунды числом и переносит пункты из одного общего поля в `keyPoints`/`points`. Раньше такой ответ считался «не-JSON» и прогон падал, хотя конспект в тексте был.
* **Markdown вместо JSON — это конспект, а не ошибка.** Если модель проигнорировала схему и написала заголовки и списки, текст принимается сразу, без лишнего запроса «почини JSON». Простой ответ без разметки становится TL;DR и разделом; приветствия и отказ («извините, не могу») по-прежнему не принимаются, а эхо самой схемы не выдаётся за конспект.
* **Повтор после пустого ответа просит упрощённую схему.** Вместо того же большого JSON с `length: 'short'` модель получает компактный формат `tldr` / `keyPoints` / `sections[{heading, points}]` — его осиливают и слабые бесплатные модели. Обрезанный ответ не запускает второй такой же запрос: бюджет увеличивается, а не повторяется.
* **Обрыв ответа не склеивается в «валидный» JSON.** Поиск блока останавливается на первой незакрытой скобке, поэтому срезанный документ больше не спасается как один вложенный фрагмент и не превращает `BAD_JSON` в ложный `EMPTY_RESULT`.
* **Таймкоды разделов не теряются при нормализации.** Обнаружено браузерным E2E: приведение разделов к каноническому виду отбрасывало `at`/`ts`, и заголовки переставали группироваться по времени. Теперь таймкод раздела сохраняется, а пункты раздела не дублируются в `keyPoints` (иначе `normalizeResult` вычитал их из раздела).
* **Аудит безопасности перед публикацией.** Убран мёртвый путь `html:` → `innerHTML` в контент-скриптах; ссылки на странице настроек строятся только из `http(s)` (`safeHttpUrl`) — `javascript:` из импортированного конфига больше не выполнится в origin расширения, где лежат ключи; `DOWNLOAD` принимает только текстовые MIME; ключ провайдера привязан к подписи endpoint и удаляется, если провайдера перенаправили на другой `baseUrl` (в том числе импортом конфига); импорт ключей уважает режим «только на время сессии»; мост страницы и слушатели `message` дополнительно сверяют `event.origin`. Добавлены регрессии на каждый пункт.
* **Устойчивость к мусору в ответе.** `normalizeResult` больше не падает на строке вместо массива, объект в `tldr` не превращается в `[object Object]`, Python-литералы `True`/`False`/`None` разбираются как JSON, `timeLink` игнорирует нечисловую позицию. Новый `tests/robustness.test.mjs` — враждебный корпус, проверка загрязнения прототипа, 200 детерминированных фазз-прогонов.
* **Лицензия — AGPL-3.0.** Полный текст в `LICENSE`; упоминания в README, `package.json` и на странице настроек обновлены.
* **Проверено.** `npm test` — 361/361 (новые регрессии: обёртка и русские поля, строки-маркеры с таймкодами, Markdown-конспект и его отличие от отказа, Markdown после неудачного ремонта, компактная схема повтора, обрыв документа, сохранение таймкода раздела, враждебный корпус и фазз, привязка ключа к endpoint, импорт ключей, allowlist скачиваний, `safeHttpUrl`), `npm run check`, `npm run build` (Chrome + Firefox), `npm run e2e` в настоящем Chrome (черновик, итог, ошибка провайдера, AUTH, таймкоды разделов).
* **Ограничение.** Живой прогон на OpenRouter не выполнен: ключа в этой среде нет. Устойчивость проверена mock-провайдерами на типичных отказах слабых моделей (обёртки, чужие поля, Markdown, пустой и обрезанный JSON); живой YouTube по-прежнему недоступен из этой среды.

## 1.6.3 — 2026-10-25 (ложный «Фоновый процесс не ответил», вердикт модерации вместо BAD_JSON)

* **«Фоновый процесс не ответил» больше не убивает исправный прогон.** Панель считала признаком жизни только сообщения задачи и отбрасывала ответы на собственный keepalive (`pong` приходит без `taskId`). Модель с режимом рассуждений молчит минутами перед первым токеном, а итоговая сборка не присылает событий до самого конца — через 30 с панель отключала порт и отменяла живой запрос, показывая эту карточку. Теперь таймер простоя сбрасывает любое сообщение порта, включая пинг-ответ; ошибкой остаётся только полная тишина (нет ни событий, ни ответов на пинги). Тот же сторож добавлен в Q&A: вопрос больше не может висеть бесконечно.
* **Модель-классификатор больше не читается как «Модель ответила текстом без JSON».** Бесплатный роутер иногда отправляет запрос модели проверки безопасности, и та отвечает одной строкой «User Safety: safe». Ответ попадал в обычный текст → `BAD_JSON` → ещё один (заведомо бесполезный) JSON-repair тем же промптом. Теперь это отдельный код `MISROUTED_MODEL`: роутер получает дополнительную попытку (вердикт приходит мгновенно), а если она не помогла — карточка с заголовком и подсказкой на языке панели и кнопкой настроек (раньше английская панель смешивала свой заголовок с русским текстом фона). Заодно починен тест, который «проверял» безопасный вердикт и на деле ничего не проверял: `withFetch` возвращает `{ res, calls }`, а код ошибки читался у обёртки.
* **Карточка с тупиком.** Когда оба маршрута субтитров падали, а фон лишь исчерпывал свой 25-секундный бонусный бюджет, панель показывала «Фоновый процесс не ответил» с одной кнопкой «Повторить». Теперь причиной становится ответ страницы («панель не нашлась», PO-token, пустая дорожка), и в карточке есть «Взять транскрипт со страницы» и «Показать транскрипт на YouTube».
* **Проверено.** `npm test` — 334/334 (новые регрессии: пинги держат прогон живым, полная тишина остаётся ошибкой, причина страницы важнее бюджета воркера, однострочный вердикт классификатора и его повтор), `npm run check`, `npm run build` (Chrome + Firefox), `npm run e2e`, `npm run e2e:rounds -- --cycles 20` — 20/20 (медиана 2,8 с, максимум 3,7 с, 20 запросов к модели). В браузерном E2E два новых сценария на настоящем Chrome: ответ модели-классификатора (`User Safety: safe`) переигрывается и даёт готовый конспект, а 35-секундная тишина провайдера — дольше сторожевого таймера панели — больше не убивает исправный прогон.
* **20 циклов E2E: гонка настроек цикла.** Повторный прогон после сборки дал 4/20: начиная с пятого цикла повторный ролик получал готовый конспект из кэша, и в запрос к моку не попадал ни один фрагмент. Запись настроек цикла (`cache.enabled: false`, `ai.useCache: false`, `chunkCache: false`) не проверялась: если она не успевала примениться, кэш оставался включённым, а тест принимал ответ из кэша за свежий. Харнесс теперь читает настройки обратно после записи и падает с понятной ошибкой «настройки не применились», а не с «фрагменты не попали в запрос». После правки — 20/20, 20 запросов к модели, медиана 2,8 с, максимум 3,7 с.
* **Живой прогон не выполнен: прокси не слушает.** `OSUM_CHROME_PROXY=socks5://127.0.0.1:12334 npm run e2e:youtube -- --cycles 20` завершился на загрузке страницы: `net::ERR_PROXY_CONNECTION_FAILED`. Прямой `curl https://www.youtube.com/` — таймаут 20 с, порты 12334 и 9150 закрыты, процесса прокси нет. Живая проверка остаётся отдельной сетевой командой и в обязательный набор не входит; после запуска прокси её нужно повторить.

## 1.6.2 — 2026-10-25 (ошибка «PO-token» убрана, 20 циклов E2E, быстрее панель)

* **«YouTube не отдал текст субтитров: дорожка защищена PO-token» больше не появляется после удачного чтения панели.** Настоящая причина была не в YouTube, а в панели: транскрипт, прочитанный со страницы (`page-capture`, `page-panel`, `page-panel-api`), не считался «готовым» и не уходил в фоновый процесс. Тот шёл за субтитрами сам, получал отказ PO-token — и весь прогон падал с этой карточкой, хотя текст уже был на руках. Теперь правило обратное: заново запрашиваются только дорожки, добытые самим фоном (`captions-*`, `legacy`, `timedtext`). Добавлен регрессионный тест на все источники.
* **Мост в мир страницы переживает CSP YouTube.** `<script src="chrome-extension://…">` подчиняется `script-src` страницы, а YouTube не перечисляет там происхождение расширения: скрипт молча не выполнялся, и все страничные маршруты ждали 25 секунд впустую. Теперь успех определяется собственным сообщением `ready` от моста, а при блокировке тот же файл инжектится через `scripting.executeScript({ world: 'MAIN' })` — на него CSP страницы не распространяется. После неудачи мост не дёргается на каждом чтении (пауза 30 с).
* **`get_panel` берёт свежие `params`.** После перехода между видео без перезагрузки (SPA) `window.ytInitialData` всё ещё принадлежит первому ролику: запрос с ними получает 400 «Precondition check failed». Мост сначала спрашивает живое дерево страницы (`ytd-app.data.response`) и только потом глобалы, с общим бюджетом на все попытки.
* **Страничный и фоновый маршруты идут наперегонки.** Раньше они запускались друг за другом: заблокированный caption-API стоил минуты ожидания, прежде чем страницу вообще спрашивали. Теперь первый результат побеждает, проигравший отменяется (панель не открывается зря), а у фонового маршрута есть потолок 25 с — «чёрная дыра» в сети больше не держит прогон.
* **Панель не остаётся в «Получаю транскрипт…» навсегда.** Тихое соединение с фоном — это ошибка с действием (`WORKER_SILENT` через 30 с без событий), а не вечная кнопка «Стоп». После получения транскрипта статус честно меняется на «Готовлю конспект…».
* **Переключение на вкладку «Расшифровка» больше не закрывает панель.** `findTranscriptTabs` хватал кнопку «Показать текст видео» — она тоже содержит слово «транскрипт», но нажатие на неё открытую панель закрывает. Сначала ищутся настоящие вкладки (`role="tab"`), и только потом — кнопки внутри панели.
* **Чтение панели сериализовано.** Два одновременных чтения (запуск конспекта во время загрузки транскрипта) открывали и закрывали панель друг друга и оба сообщали «не нашлась». Чтения выстроены в очередь.
* **Чтение панели без лишнего ожидания.** Когда ролик открывается только через панель «Транскрипт», страница не делает собственного запроса `get_panel`, и подписка на его ответ ждала все 4 с. Ожидание сокращено до 1,5 с (ответ приходит раньше): маршрут `page-panel` подешевел с 4,6 с до 2,07 с на цикл, при этом набор фрагментов не изменился.
* **20 циклов E2E в настоящем Chrome.** Новый `npm run e2e:rounds` прогоняет полный путь на локальных копиях разметки: захват ответа панели (та самая PO-token ситуация), обычные строки, «Эпизоды» и поздняя кнопка. Отчёт — `dist/e2e-rounds/report.json`, бюджеты на цикл. Прогон 20/20: медиана 2,8 с, максимум 3,7 с, каждый транскрипт дошёл до модели. `npm run e2e:youtube -- --cycles 20` остаётся живой сетевой проверкой.
* **Живой YouTube: 20 циклов, 20/20.** Первый живой прогон нашёл реальный сбой, которого нет на копиях разметки: на медленном канале страница уже отдала транскрипт, а повторное чтение (после которого панель ждала ещё и фон) не находило панель — и готовые 23 фрагмента выбрасывались вместе с ошибкой «Фоновый процесс не ответил». Теперь, если обновление транскрипта упало, но этот же ролик уже есть в памяти, конспект строится по нему (`TRANSCRIPT_REUSED` в журнале), а не показывается карточка. После правки — 20/20 на настоящем видео, медиана 17,7 с на цикл (канал — локальный SOCKS-прокси, поэтому секунды — сеть, а не код); в каждом цикле в промпт ушло 928 слов. Журнал живого прогона подтверждает реальные отказы: `page-api` 400, `timedtext` POT_REQUIRED, `get_transcript` 403 и успешный `page-capture`.
* **Тестовый браузер можно провести через свой прокси.** `OSUM_CHROME_PROXY=socks5://127.0.0.1:9150` добавляет `--proxy-server` только тестовому Chrome: на сети, где `youtube.com` не открывается напрямую, живая проверка больше не требует менять системные настройки. Отказ SOCKS-соединения повторяется один раз (это транспорт, а не «нет субтитров»), а `--cycles N` теперь считает доставку по таймкодам и словам настоящего промпта — прежний счётчик искал маркеры синтетической фикстуры и печатал отрицательные числа.
* **Проверено.** `npm test` — 329/329, `npm run check`, `npm run build`, `npm run e2e`, `npm run e2e:rounds -- --cycles 20` (20/20; `capture` 0,55 с, `rows` 2,07 с, `chapters` 2,83 с, `late` 3,4 с), `npm run e2e:youtube -- --cycles 20` на настоящем ролике (20/20), `npm run quality` (границы чанков 27–40 % на смене темы).
* **Ограничение.** Прямого доступа к `youtube.com` из этой среды нет (TCP до ролика не устанавливается), поэтому живой прогон шёл через локальный SOCKS-прокси: он меняет только задержку (17,7 с на цикл вместо 2,8 с на локальных копиях), но не разметку и не ответы YouTube. С одним роликом на английском; другие языки и автоматические дорожки живьём не перепроверены.

## 1.6.1 — 2026-10-24 (настройки сохраняются, два режима конспекта, палитра YouTube)

* **Выбор в быстрых настройках больше не теряется.** Язык, объём и новый режим конспекта меняли только состояние в памяти панели: при следующем открытии строка возвращалась к старым значениям. Теперь каждое изменение уходит в `save-settings` (`persistMode`) и приходит обратно из `chrome.storage`, а провайдер по умолчанию записывается один раз, если в настройках его не было (раньше диагностика показывала «active: —», хотя прогон шёл через OpenRouter).
* **Два режима конспекта: «Вся запись» и «По таймкодам».** Новый `ai.summaryMode` (переключатель в быстрых настройках и в окне настроек). `whole` — прежний путь: весь транскрипт (или чанки) уходит в модель, это режим по умолчанию. `timeline` — как у суммаризаторов, которые идут по таймингам: главы/блоки видео обрабатываются по очереди, каждый ответ даёт свой раздел с таймкодом, а итог собирается из них. Панель показывает разделы по мере готовности.
* **«Вопросы для самопроверки» больше не пробиваются в конспект.** Настройка `output.selfCheck` по умолчанию выключена; промпт просит `questions: до 0`, а конвейер дополнительно очищает поле в обоих путях (фрагментами и одним ответом) — слабые модели писали блок «несмотря на инструкцию», и он попадал на экран.
* **Страница не прокручивается на глазах пользователя.** Чтение панели «Транскрипт» остаётся невидимым: скрывающие стили ставятся до появления панели, держатся всё время чтения и снимаются только когда узла панели действительно нет в документе (включая анимацию закрытия). Первая проверка — синхронная, поэтому чтение не может завершиться с ещё навешанными стилями; прокрутка пользователя по-прежнему приоритетнее.
* **Заголовок раздела — одна кнопка перехода.** Клик по словам заголовка (не только по цифрам) перематывает видео; таймкод главы не повторяется в её первом пункте.
* **Неполный конспект честно помечен.** Если фрагмент не обработан, конспект не выдаётся за полный: в предупреждениях — «Не обработано фрагментов: N из M» с диапазоном времени, `meta.complete: false`, задание остаётся продолжаемым, а в подвале прямо сказано, что покрыта только часть видео.
* **Тёмная палитра — как у окна транскрипции YouTube.** Панель, страница настроек и popup перешли на нейтральные ступени YouTube: `#0f0f0f` страница, `#212121` поверхность, `#272727`/`#303030` приподнятые блоки, `#3f3f3f` волосяные линии, `#f1f1f1` текст, `#aaaaaa` вторичный. Синевато-серые `#16181d`/`#212531` и фиолетовая заливка тонких блоков убраны — рядом с «В этом видео» панель читалась как чужое окно. Светлая тема не менялась.
* **Проверено.** `npm test` — 322/322, `npm run check`, `npm run build`, `npm run e2e`: в настоящем Chrome добавлены утверждения палитры для панели, настроек и popup (`#0f0f0f`/`#212121`/`#f1f1f1`), плюс прежние сценарии — черновик, итог, ошибка провайдера, AUTH, быстрые настройки, «Подробности запуска».
* **Ограничения.** Живой прогон на OpenRouter в этом выпуске не выполнялся: присланный ключ отклонён (`401 User not found`). `npm run e2e:youtube` — отдельная сетевая проверка, в обязательный набор не входит.

## 1.6.0 — 2026-10-23 (один движок — ИИ, страница не дёргается, аккуратные подложки)

* **Суммаризация без ИИ удалена целиком.** Локальный экстрактивный движок (`summarizeLocal`), его настройки в окне настроек, переключатель движка в панели, popup, кнопка «Сделать локально» в карточках ошибок, сообщение `local-summary` и весь путь перевода готового конспекта (Google/MyMemory/LibreTranslate) убраны. Конспекты локального движка были набором повторов и обрывков, и поддерживать два качества в одном продукте больше не имеет смысла. Резервный **поиск** по транскрипту (BM25) остался только в Q&A: он цитирует фрагменты и ничего не придумывает.
* **Страница больше не смещается при чтении транскрипта.** Панель YouTube, которую расширение открывает в фоне, по-прежнему уходит за экран до появления и закрывается после чтения, но теперь восстанавливается не «число прокрутки», а **положение плеера на экране**: YouTube меняет высоту боковой колонки и описания, и прежний `scrollTop` указывал уже в другое место. Если пользователь сам прокрутил страницу, его позиция не трогается.
* **Наведение на заголовок — подложка, а не подчёркивание.** Строка заголовка раздела (и пункт-ссылка) подсвечивается мягкой плашкой; подчёркивание через две строки читалось как сломанная ссылка.
* **Переключатель темы — эмодзи.** Вместо самодельной иконки ☀️/🌙: системный эмодзи однозначен на любом размере. Шестерёнка появилась и перед текстом «Все настройки» — та же, что в шапке.
* **«Подробности запуска» внутри области чтения.** Блок был отдельным flex-элементом панели: он не сжимался, содержимое уезжало под нижнюю полосу, а вторая полоса прокрутки пересекала карточки. Теперь у него одна прокрутка вместе с конспектом, ритм 12 px между блоками и сетка статистики, которая переносится вместо обрезки справа.
* **Промпт: один факт — один раз.** Правила требуют не пересказывать пункты разделов в `keyPoints`, не повторять один факт в разных разделах, не выдавать TL;DR за список тем через запятую и писать имена и термины так, как они звучат в транскрипте (искажённые «Дуааджа» и «сверер интеллект» — ошибка). `PROMPT_VERSION` поднят до 3, так что кэш фрагментов старого промпта не подмешивается.
* **Ошибка больше не прячет готовый конспект.** Если обновление не удалось, карточка с причиной появляется **над** уже показанным конспектом, а не вместо него.
* **Проверено.** `npm test` — 300/300, `npm run check`, `npm run quality`, `npm run build`.
* **Ограничения.** Живой провайдер и настоящий YouTube в этом прогоне не участвовали; `npm run e2e:youtube` не запускался.

## 1.5.0 — 2026-10-22 (светлая тема, перевод без ключа, без карты, быстрее)

* **Светлая тема по умолчанию и переключатель.** Панель — документ для чтения, поэтому по умолчанию она белая (раньше наследовала тему YouTube и на тёмном сайте была тёмной). В шапке — солнце/луна, выбор темы продублирован в «Настройках»: светлая, тёмная или как на YouTube. Тема хранится в `ui.theme` и применяется без перезагрузки страницы.
* **Карта видео удалена.** Двадцать колонок «плотности» ничего не говорили о содержании и занимали пол-экрана. Вместо неё — разделы, как в конспекте Яндекса: **вся строка заголовка — ссылка на момент**, а не только цифры таймкода. Таймкод остался акцентной плашкой внутри кнопки, чтобы не терять ориентир. Это же работает для подзаголовков-пунктов: таймкод в них кликабелен.
* **Главная кнопка крупнее и с текстом.** «Суммировать» / «Обновить» / «Стоп» — 36 px высотой, с иконкой и подписью; раньше это была иконка-загадка, которую приходилось угадывать. Шестерёнка нарисована настоящим зубчатым колесом (восемь зубцов и кольцо) и стала читаемой в 30 px кнопке.
* **Перевод без ИИ снова работает — и быстрее.** Keyless-переводчик Google (`translate_a/single`, без ключа и без дневного лимита) стал первым в цепочке «Авто», MyMemory — резервным. Строки конспекта переводятся параллельно, по четыре запроса: тот же конспект из девяти фрагментов занял **2,0 с вместо 9,1 с**. Если часть строк не перевелась, панель применяет переведённое и честно пишет, что часть осталась на языке видео, вместо того чтобы выбросить весь перевод. Ошибка показывает `hint` переводчика.
* **ИИ больше не сдаётся на `TRUNCATED`.** Две причины двойного провала закрыты: Gemini 2.5 считает токены размышления внутри `maxOutputTokens` — Flash теперь получает `thinkingBudget: 0`, Pro — минимальные 128; базовый бюджет стандартного конспекта поднят до 5000, эскалация — до 16 000 (потолок из настроек), фрагменты map-фазы — 4096 (это лимит, а не расход). Если ответ обрезан и после увеличения лимита, делается третий запрос в коротком формате на тот же потолок; только после него — спасение полного префикса, пометка «неполный» и переход на фрагменты. В подсказке ошибки прямо сказано, что делать.
* **Скорость.** Перевод распараллелен; потоковые пункты в панели схлопываются в один `render` на кадр (`requestAnimationFrame`) вместо полной перерисовки на каждый пункт; лишние 1000-сегментные прогоны не создают запросов. Замеры в настоящем Chrome (`npm run e2e`): открытие панели — **104 мс**, готовый ответ после релиза мока — **212 мс**, локальный конспект 1000 фрагментов через фон и рендер — **677 мс**. Эти числа теперь проверяются бюджетами в e2e (2500 / 3000 / 5000 мс), а не только печатаются.
* **Проверено.** `npm test` — 341/341, `npm run check`, `npm run build`, `npm run e2e` (реальный Chrome: черновик, итог, отсутствие карты, кнопка-заголовок с таймкодом, фолбэк, AUTH, замеры скорости), `npm run quality`.
* **Ограничения.** Онлайн-прогон `npm run e2e:youtube` в этом сеансе не выполнялся. `thinkingBudget` выставляется только моделям Gemini 2.5: у 2.0 параметра нет, у 3.x другая схема. Google Translate — неофициальный keyless-endpoint; при его блокировке остаётся MyMemory с дневным лимитом 5 000 символов. Живой провайдер ИИ в замерах не участвовал: числа скорости относятся к интерфейсу и локальному движку, а не к сети модели.

Теперь `inject.js` ставит флаг `window.__osumBooted`, `mount()` сначала убирает осиротевшие `#osum-host`, а `render()` держит `hidden` у кнопки в единственном месте — по `panelOpen`.
* **Таймкод главы больше не дублируется в её первом пункте.** В разделе с заголовком «1:30» первый пункт того же времени больше не показывает такой же таймкод: оба вели в одно место. Пункт, который позже, свой таймкод сохраняет.
* **«Вопросы для самопроверки» — выключены по умолчанию.** Для обоих движков это теперь одна настройка `output.selfCheck` с галочкой в «Всех настройках»; в промпте ИИ вместо `questions: до 3/5` стоит `до 0`, и слабая бесплатная модель не тратит на них выходной бюджет, которого не хватает конспекту. Локальный движок получает `quiz` из той же настройки.
* **Остаток времени — живой.** Вместо статичного «Осталось: 6:10 / 6:10», которое менялось только с приходом события прогресса, — «Осталось ~6:10», каждую секунду пересчитанное от дедлайна задания. Точка правки — только текст строки, полный перерисовки нет.
* **Перевод локального конспекта — по кнопке.** «Без ИИ» и раньше не переводил сам, а чтобы включить перевод, нужно было идти в настройки. Теперь под конспектом на другом языке есть кнопка «Перевести на …»: нажатие включает бесплатный переводчик (MyMemory) и переводит уже готовый текст — на сервис уходят только строки конспекта, никогда транскрипт. Ошибка перевода оставляет конспект как есть и показывает причину. Новое сообщение `translate-summary` в `MSG`.

В шапке осталась одна кнопка «Копировать транскрипт» (текст с таймкодами в буфер обмена). Теперь `normalizeResult` один раз сортирует таймированные пункты, разделы и пункты внутри разделов по возрастанию времени; пункты без таймкода остаются в конце, а не выдают себя за 0:00. В живом черновике порядок тот же.

Заголовок карты теперь переводится («Карта видео» / «Video map»).

Перекрытие — один блок вместо прежнего «хвоста по токенам».

При `maxTokens=6000` — 40% границ на смене темы и 1% пересмотра. Число чанков не выросло (12 → 12 и 6 → 6).
* **Локальный движок не берёт «в этом видео я расскажу» в конспект.** `isMetaTalk` помечает служебные реплики о самом ролике (подписка, лайк, «давайте начнём», «как вы знаете»), и они не попадают ни в TL;DR, ни в ключевые пункты — раньше именно они открывали конспект.
* **Проверка чисел и цитат в ИИ-ответе.** Новый `src/ai/verify.js` сверяет каждое число из конспекта с числами транскрипта (с учётом запятой/точки) и проверяет дословность цитат. Неподтверждённые числа и цитаты попадают в `meta.grounding`, в предупреждения результата и в «Run details» с подписью «проверьте по источнику». Ответ не переписывается: модуль ничего не исправляет и не делает вид, что проверил смысл — причинные связи и перевод вне его возможностей, это написано в модуле и в подсказке.
* **`npm run quality`.** Офлайн-отчёт без модели и сети: время локального движка, «пустые» и повторные заголовки, доля дублей в пунктах, а для чанкера — границы на смене темы, пересмотренные токены и сравнение с размерной нарезкой при двух лимитах. Синтетический транскрипт размечен темами, поэтому «заголовок из местоимений» и «граница посреди темы» стали числами, а не мнением.
* **Проверено.** `npm test` — 334/334, `npm run check`, `npm run build`, `npm run e2e` (реальный Chrome: черновик, итог, непустая «Таймлайн» из 20 корзин, фолбэк, AUTH; вставка текста теперь идёт через быстрые настройки), `npm run quality`.
* **Ограничения.** Стенд `quality` синтетический: он не доказывает качество на реальном видео и не измеряет модель. Проверка чисел не ловит выдуманные утверждения без цифр и перефразированные цитаты. Живой провайдер и настоящий YouTube в этом прогоне не участвовали.

## 1.4.12 — 2026-10-21 (проверка разбора на сохранённом ответе YouTube)

Вход — сохранённая watch-страница или `.json` с `ytInitialPlayerResponse`.
* **Очистка до записи.** Значения параметров URL, кроме `v`, `lang`, `fmt`, `kind`, `tlang`, `hl` и маркера `exp=xpe`, заменяются на `REDACTED`; выбрасываются `trackingParams`, `playbackTracking`, `playerConfig`, `visitorData` и прочие служебные блоки; `getTranscriptEndpoint.params` заменяется заглушкой с сохранением пути. `auditFixture` проверяет результат на живую подпись, JWT, API-ключ и длинные токеноподобные литералы — при находке файл не пишется. Сравнение разбора до/после очистки печатается как «паритет»; при расхождении команда завершается кодом 1.
* **Уровни A/B/C разделены.** A — синтетические тесты (`npm test`); B — настоящий сохранённый ответ (`tests/fixtures/youtube/*.json`, пока файлов нет тест печатает «ожидается fixture» и ничего не утверждает); C — живое скачивание субтитров, в этой среде недоступно. Успешный офлайн-тест не повышает уровень подтверждения.
* **`PARSE_FAILED` и `NO_TRACK_SELECTED`.** Журнал теперь различает отказ скачивания (HTTP-код маршрута), пустую дорожку (`EMPTY_CAPTIONS`), ответ, который пришёл, но не разобрался (`PARSE_FAILED` с форматом и размером тела), и ситуацию «дорожки есть, ни одна не выбрана». В журнал пишется сводка попыток по форматам (`json3:PARSE_FAILED · vtt:403`). Раньше эти случаи сливались в один код `EMPTY_CAPTIONS`. `PARSE_FAILED` выдаётся только на нераспознанное или обрезанное тело: валидный контейнер без реплик (`{"events":[]}`, VTT без `-->`, пустой `<transcript/>`) остаётся `EMPTY_CAPTIONS` — иначе код означал бы «ошибка декодирования» и «неподдерживаемый формат» одновременно.
* **Подсказка в панели.** Для `PARSE_FAILED` добавлен `parseFailedHint` (ru/en) с предложением взять транскрипт со страницы или вставить текст вручную; оба кода не запускают переключение провайдеров.
* **Документация.** `tests/fixtures/youtube/README.md` — как снять ответ, что именно вычищается и почему fixture не доказывает скачивание; команда `npm run fixture` описана в README.
* **Проверено.** `npm test` — 317/317 (11 новых: 9 уровня A, 1 уровня B с честным «ожидается fixture», 1 про разделение отказов в журнале), `npm run check`, `npm run build`, `npm run e2e`. Синтетический образец прогнан через `analyze` и `sanitize`; очищенный файл проходил собственный аудит, паритет разбора — OK.
* **Ограничения.** Настоящий fixture в репозиторий не добавлен: снять его в этой среде нельзя (TLS-reset на домены YouTube подтверждён и браузером, и терминалом). Разбор реального ответа и живое скачивание остаются непроверенными; PO-token и срок жизни подписанных URL зависят от клиента и меняются со временем.

## 1.4.9 — 2026-10-21 (поток: протокол, повторы и границы частичного ответа)

* **CRLF-поток больше не теряется.** Границей SSE-события считался только `\n\n`; ответ с `\r\n\r\n` не делился вообще, весь текст разбирался одной строкой в конце — где склейка нескольких `data:`-строк уже не была валидным JSON, и исправный ответ заканчивался `EMPTY_RESPONSE`. Теперь буфер нормализует `\r\n` → `\n`, включая разрыв `\r\n\r` + `\n` между сетевыми чанками.
* **`[DONE]` завершает чтение.** Провайдер или прокси, оставляющий keep-alive соединение открытым после `[DONE]`, раньше приводил к `TIMEOUT` уже после полного ответа. Теперь явные маркеры (`[DONE]`, Ollama `done:true`, Anthropic `message_stop`) освобождают reader вместо ожидания EOF.
* **`finish_reason: "error"` — ошибка, а не успех.** Такой чанк раньше доходил до парсера как обычный ответ; теперь это `PROVIDER_ERROR` с подсказкой. Заодно причина завершения теперь доходит из потоковых ответов Google (`finishReason`), Anthropic (`stop_reason`) и Ollama (`done_reason`): без этого `MAX_TOKENS` у Google не считался обрезанным ответом.
* **Повтор после оборванного потока начинает чистый черновик.** Внутренний retry клиента продолжал кормить тот же инкрементальный парсер: второй ответ приклеивался к обрезанной строке первого, и в панели мог появиться мусор. Теперь у каждой попытки свой парсер и свой `streamId`, счётчики `streamFirst*`/`streamItems` сбрасываются, а панель заменяет черновик. Один и тот же пункт, пришедший дважды, показывается один раз.
* **Ошибка не оставляет соединение висеть.** При исключении внутри потока reader отменяется, слушатель abort снимается в `finally`.
* **Вкладка «Транскрипт» больше не скрывает результат.** Вставка текста запускает конспект, не уводя с вкладки «Транскрипт»: черновик и готовый конспект рисуются на «Обзоре», поэтому пользователь без субтитров видел только счётчик, а после завершения — пустую вкладку. Запуск теперь переключает панель на «Обзор».
* **Причина дедлайна больше не теряется.** Если fetch отклоняется синхронно на abort чуть раньше записанного мгновения дедлайна, ошибка получала деталь `aborted` вместо `job-deadline`. Причина abort (`job-deadline`) теперь проверяется наравне с часами; пользовательская отмена по-прежнему остаётся отменой.
* **Живой прогон в Chromium.** Unpacked-сборка загружена в настоящий Chrome 155 (headless, CDP `Extensions.loadUnpacked`); страница-заглушка и SSE-провайдер — на loopback. Проверено: 40 фрагментов вставленного текста доходят до запроса; черновик (TL;DR и пункт) виден, пока сервер держит остаток, без сырого JSON и без готового конспекта; после завершения — полный конспект с поздним пунктом; обрыв ответа даёт локальный фолбэк с причиной `PROVIDER_ERROR`; отклонённый ключ — карточку `AUTH` с подсказкой и без конспекта. Проверка шла по DOM панели в Shadow DOM и по скриншотам.
* **Проверено:** `npm test` — **306/306**; 20 новых тестов: CRLF с разрезом внутри `\r\n`; `[DONE]` без закрытия соединения (и то же для Ollama и Anthropic); `finish_reason:error`; keepalive-комментарии между событиями; BOM перед первым событием; HTML-тело HTTP-ошибки не попадает в сообщение; обрыв посреди JSON даёт `BAD_JSON`, а не «готовый» конспект; reasoning-дельты не идут ни в дельты, ни в элементы; повтор после обрыва даёт новый `streamId` и чистые пункты; Google SSE с разрезом на `candidates` и `MAX_TOKENS`, помеченный как обрезанный; пустые служебные чанки не теряют usage и finish; обрыв посреди ответа не создаёт ни результата, ни записи в кэше; сквозной тест на настоящем loopback-сокете (CRLF, разрез посреди ответа, элемент приходит, пока сервер ещё держит остаток); в панели — замена черновика при смене `streamId` и отсутствие дублей; на уровне воркера — `stream-item` действительно доходит через порт с `streamId` и `item`, а счётчик диагностики совпадает с числом полученных событий; переключение с «Транскрипта» на «Обзор» при запуске; деталь `job-deadline` при синхронном отказе fetch. `npm run check`, `npm run build` (Chrome/Firefox).
* **Ограничения:** живого провайдера нет (SSE-мок повторяет формат OpenAI), а браузерный прогон идёт на локальной странице-заглушке, а не на настоящем YouTube: разметка и субтитры YouTube этим прогоном не проверяются. С 1.4.10 этот прогон закреплён как `npm run e2e`. Reasoning остаётся запасным источником текста для финального JSON (так отвечают некоторые free-маршруты), но не показывается как конспект и не попадает в потоковые элементы. Планировщик, промпт и Map/Reduce не менялись.

## 1.4.8 — 2026-10-20 (проверенные пункты появляются по ходу одного ответа)

* **Ранний результат без дополнительных запросов.** В single-pass ответ приходит одним JSON-объектом, и раньше до закрывающей скобки в панели был только счётчик и сырой текст. Теперь `src/ai/stream-json.js` разбирает поток по мере поступления: как только значение `tldr`, элемент `keyPoints` или `sections` закрыт и прошёл ту же проверку, что и финальный разбор (`normalizePoint`/новая `normalizeSection`), он публикуется событием `stream-item` и появляется в панели карточками. Число запросов не меняется: это тот же один вызов модели, никаких предварительных суммаризаций.
* **Почему фиксированная схема, а не универсальный JSON-парсер.** Известны только нужные поля; остальное пропускается подсчётом скобок и строк. Разбор идёт одним проходом по накопленному тексту с сохранённой позиции (O(total), без повторного парсинга на каждый токен), границы сетевых чанков могут попадать куда угодно — в середину ключа, строки, escape-последовательности, суррогатной пары. Нормализация та же, что у финального результата, поэтому показанный пункт совпадает с тем, что останется в конспекте.
* **Что именно показывается.** TL;DR, ключевые пункты и разделы, в порядке схемы; у разделов видны заголовок, таймкод, краткое содержание и до трёх пунктов. Плейсхолдеры схемы («строка: …», «тема»), пустые объекты и точные повторы отбрасываются; ограничения (24 пункта, 20 разделов) совпадают с `normalizeResult`, поэтому живой вид не может оказаться длиннее готового.
* **Сырой JSON больше не показывается.** Блок с «хвостом» потока в статусе убран: непроверенные фрагменты — не результат, и перерисовка на каждый токен только заставляла панель мигать. Вместо него — нормальные карточки и строка «Готово пунктов: N …»; прокрутка сохраняется (обновляется тело, а не весь экран скачком).
* **Провал и отмена — не «готово».** Если поток оборвался, пришла ошибка или пользователь нажал «Стоп», уже проверенные пункты остаются на экране, но с подписью «Ответ не завершён: показана только проверенная часть», а результат по-прежнему не считается полным: `complete=false`, кэш не пишется. Повтор с большим лимитом ответа получает новый `streamId`, и панель начинает черновик заново, не склеивая два разных ответа. Отмена прекращает чтение сразу, без нового запроса.
* **Диагностика.** В `meta.diagnostics` добавлены `streamFirstTextMs`, `streamFirstItemMs`, `streamItems`, `streamKeyPoints`, `streamSections`, `streamTldr` — всё измеренное, без оценок. Они же попадают в отчёт `npm run bench -- --live`, так что живой прогон покажет, сколько времени ушло до первого проверенного пункта.
* **Замер (стенд, не провайдер).** `node tools/bench.mjs --live --mock --synthetic` поднимает локальный SSE-мок и прогоняет настоящий конвейер; `--no-stream` отвечает тем же JSON целиком в конце, поэтому разница показывает именно эффект потока. По три прогона: медиана до первого текста — 104 мс, до первого проверенного пункта — **293 мс при полном ответе 1,61 с**; в непотоковом режиме первого пункта нет до самого конца (1,31 с). Итог совпадает по всем полям (TL;DR 147 символов, 3 ключевых пункта, 1 раздел), запрос в обоих режимах **один**. Абсолютные секунды — это заданный темп мока плюс разбор, а не скорость модели; TTFT реального провайдера здесь не измеряется.
* **Проверено:** `npm test` — **286/286** (разбор по одному символу; отсутствие элемента до закрытия значения; плейсхолдеры и точные повторы; escape, перевод строки и эмодзи на границе чанков; snake_case-алиасы; поступление пунктов до закрытия потока через управляемый мок; совпадение потокового и обычного результата по всем полям; ошибка посреди потока не даёт `complete`; отмена без второго запроса; в панели — черновик до финального результата и проверенная часть под ошибкой), `npm run check`, `npm run build` (Chrome/Firefox).
* **Ограничения:** живой модели не было — ключа в среде нет, поэтому реальный выигрыш зависит от TTFT и скорости генерации провайдера; полное время до TL;DR не меняется (поток не ускоряет модель); map-reduce-путь не тронут — его ранние фрагменты работают как раньше; если модель отдаёт только reasoning-дельты без видимого текста, проверенных пунктов не будет до появления JSON.

## 1.4.7 — 2026-10-20 (измерение вместо догадок: где на самом деле время)

* **Сначала измерение.** Добавлен офлайн-стенд `npm run bench:sim` (`tools/bench-sim.mjs`): он гоняет настоящий `runAiSummary` с подставным провайдером с одинаковой задержкой на вызов и печатает число запросов, волн Map, раундов Reduce, время до первого фрагмента и длину критического пути. Секунды здесь — проекция при заданной задержке вызова, а не замер API; для живых цифр остаётся `npm run bench -- --live`. Живой отчёт теперь содержит `stagesMs`, `reduceRounds`, `concurrency`, `rateLimited`, `mapPausedMs`, `mapQueueMs`, `firstPartialMs`, `chunkCounts` и список фактически выбранных моделей, а `npm run bench:report` сводит несколько прогонов в медиану с разбросом.
* **Что показало измерение.** При дефолтном контексте 128k видео на 50 минут (9 554 слова, ~27k токенов) и на 104 минуты (19 865 слов, ~57k токенов) обрабатываются **одним** запросом: Map/Reduce не запускается, структурных накладных расходов нет, всё время — обработка промпта и генерация. Для 240 минут (~132k токенов) Map делает 27 запросов шестью параллельными волнами.
* **Убран лишний раунд Reduce на длинных видео.** Бюджет входа финальной сборки был равен `chunkTokens` (6 000), то есть размеру map-фрагмента, хотя предел сборки — окно модели минус промпт и ответ. Из-за этого 7k токенов заметок трёхчасового видео уходили в иерархический раунд из двух параллельных запросов без выигрыша в качестве. Теперь `reduceInputBudget()` считается от `contextTokens`; на 240-минутном стенде: **30 → 28 запросов, 1 → 0 промежуточных раундов, критический путь 7 → 6 вызовов, −14%** (910 → 781 мс при задержке 120 мс; в проекции при 10 с на вызов 70 → 60 с). Те же 27 map-заметок и та же финальная сборка — точность не менялась.
* **Малый контекст стал безопаснее.** На модели с окном 8k сборка больше не просит 6 000 входных токенов поверх промпта и ответа: бюджет — 2 096, при необходимости добавляется раунд вместо ошибки контекста. Это исправление корректности, а не ускорения.
* **Проверено:** `npm test` — 274/274 (бюджет сборки от окна модели, потолок резерва ответа, отсутствие лишнего раунда при 128k, наличие раунда при 8k); `npm run check`; `npm run build` для Chrome и Firefox; офлайн-стенд на 50/104/240 минутах.
* **Не проверено:** живых API-запросов и браузерных прогонов не было — ключа в среде нет, git-репозитория для сравнения с прежней стабильной версией тоже нет. Поэтому целевые −25–30% общего времени на 50-минутном видео **не подтверждены**: измерение показывает, что на этой длине планировщик не является узким местом, и выигрыш может дать только генерация/модель, что требует живых прогонов.

## 1.4.6 — 2026-10-20 (общий тормоз на 429 и токены в отчёте)

* **429 тормозит весь прогон, а не один фрагмент.** Раньше получивший `RATE_LIMIT` чанк снижал общее окно параллельности, но остальные запросы из очереди уходили к провайдеру немедленно. Теперь лимитер хранит общий `readyAt`: на `429` новые фрагменты не стартуют, пока не истечёт `Retry-After` (или 2 с, если заголовка нет), уже запущенные запросы спокойно завершаются, а сниженное окно применяется ко всем следующим. Пауза ограничена дедлайном map-этапа и не может продлить задание; по истечении срока оставшиеся фрагменты пропускаются как раньше, с сохранением готовых. Это ограничитель частоты, а не разрешение на «20 RPM = 20 одновременно».
* **Backoff с jitter.** Повторные попытки внутри клиента теперь считаются `retryBackoffMs()`: экспоненциальная база 700 мс с добавкой до 25% случайности, `Retry-After` — нижняя граница, потолок 45 с. Параллельные фрагменты, получившие один и тот же 429, больше не повторяют в такт и не воспроизводят всплеск.
* **Панель показывает фактическое окно.** В прогрессе `running` теперь берётся из текущего лимитера, поэтому после 429 видно уменьшенную параллельность, а не стартовую.
* **Токены и ограничения — в отчёте.** Диагностика задания пополнилась `tokensIn`/`tokensOut` (только то, что вернул API; неизвестное остаётся нулём, а не оценкой) и `rateLimited`/`mapPausedMs`. В раскрываемом отчёте появились строки «Токены (вход → выход)» и «Ограничений частоты» с суммой пауз.
* **Ошибка фрагмента видна рядом с готовыми.** Неудачный фрагмент больше не выглядит пустым блоком: в потоковом предпросмотре у него подпись «Фрагмент не обработан» и причина, а счётчик считает только реально готовые части.
* **Проверено:** `npm test` — 272/272 (общая пауза после 429 не меняет порядок и не стартует очередь раньше срока; короткая/нулевая пауза не сокращает текущую; снижение окна и пауза независимы; токены из ответа API доходят до диагностики; неудачный фрагмент не скрывает готовые и не завышает счётчик; разбиение транскрипта без таймкодов ничего не теряет; покрытие всех блоков и хронология фрагментов; 429 с Retry-After задерживает очередь и не повторяет успешные фрагменты; jitter не сокращает Retry-After и не выходит за потолок); `npm run check`; `npm run build` для Chrome и Firefox. Живых API-запросов не было — сравнимых замеров времени до первого результата и общего времени с 1.4.4/1.4.5 нет.
* **Ограничения:** RPM/TPM по-прежнему не моделируются заранее — пауза реактивная, по фактическому 429/Retry-After; provider-specific лимиты бесплатных маршрутов OpenRouter могут отличаться от дефолтных 2 с при отсутствии заголовка; токены учитываются, только если провайдер вернул usage.

## 1.4.5 — 2026-10-20 (ранние фрагменты, честные цифры и достаточный лимит ответа)

* **Лимит ответа выбирается по фактическому входу.** На реальном видео 1:44:35 первый ответ обрезался на 4096 токенах, после чего запускался полный повтор с 8192. Теперь начальный бюджет считается по профилю длины и размеру транскрипта: база 2048/4096/6144 плюс до 3072 токенов для входов длиннее 12k, с потолком 8192. Короткое видео не платит за длинное; подробный конспект длинного видео сразу получает верхний предел. Явно заданный пользователем больший лимит по-прежнему учитывается.
* **Обрезанный ответ больше не запускает JSON-«ремонт».** Раньше `finish_reason=length` уходил в отдельный запрос починки JSON, который не мог помочь. Теперь пайплайн сразу видит `TRUNCATED` и делает один осознанный повтор с большим бюджетом. Если и он обрезан, полностью полученные поля сохраняются как **неполный** результат (`complete=false`, `finishReason=output-limit`), не кэшируются и не выдаются за готовый конспект; незавершённые строки и объекты отбрасываются, а не додумываются.
* **Единая статистика для обоих движков.** `words` считается по фактически обработанному тексту транскрипта, `summaryWords` — по итоговому телу конспекта (TL;DR, разделы с заголовками и пунктами, key points, выводы, вопросы, цитаты, ключевые слова), `compression` — как их отношение, `readingTimeSec` — от тех же слов. Модель больше не может «придумать» процент сжатия. Кэш конспекта привязан к хешу транскрипта: другая версия субтитров не отдаёт старые цифры.
* **Финальное состояние панели.** После завершения `Remaining` больше не показывается: вместо него видны фактически затраченное время и первоначальный бюджет, обратный отсчёт остаётся только у работающего задания. В раскрываемой диагностике — время, первоначальный и итоговый лимит ответа, число его повышений, время до первого фрагмента и максимальная параллельность.
* **Потоковые фрагменты длинного видео.** Map-этап уже шёл параллельно; теперь каждый проверенный ответ сразу публикуется событием `partial` и появляется в панели как «Готовые фрагменты» в исходном порядке, даже если ответы пришли вразнобой. Медленный фрагмент не задерживает остальные, ошибка одного не скрывает готовые, прокрутка сохраняется. Итоговый Reduce и TL;DR по-прежнему запускаются только после завершения всех Map-задач; предварительная версия всего конспекта не создаётся, лишних запросов нет.
* **Проверено:** `npm test` — 265/265 (бюджет по размеру входа; сохранение полей после двойного обрезания; статистика по фактическому тексту; финальная панель без `Remaining`; порядок фрагментов до Reduce; медленный фрагмент не блокирует первый результат; дедупликация точных повторов из перекрытия); `npm run check`; `npm run build` для Chrome и Firefox. Живых API-запросов не было, поэтому сравнения времени и токенов с 1.4.4 нет.
* **Ограничения:** фрагменты в панели — проверенные промежуточные заметки, а не финальный текст: Reduce может переформулировать и объединить их; потоковая выдача токенов внутри JSON не показывается (невалидный JSON не попадает в UI); RPM/TPM провайдера не моделируются отдельно — работают существующие параллельный пул, снижение конкурентности на 429 и backoff; лимит вывода модели берётся из общего потолка 8192, а не из каталога конкретной модели.

## 1.4.4 — 2026-10-20 (явное «Продолжить» и бюджет по плану, а не по страхам)

* **Кнопка «Продолжить» для прерванного задания.** Панель отдельно спрашивает фон (`get-resumable`) и показывает кнопку только тогда, когда сохранённое задание совместимо с текущим видео: отпечаток транскрипта, ревизия промпта, версия приложения, провайдер, модель, настройки вывода и язык интерфейса. Возобновляется именно это задание (`resumeJobId`), а не создаётся новая суммаризация: готовые фрагменты и их заметки, а также результаты успешных промежуточных reduce-групп берутся из `osum:jobs`; ни один успешный запрос не повторяется. Рядом видно, сколько фрагментов готово и почему прогон остановился (`job-timeout`, `call-timeout`, `incomplete`, `worker-restart`).
* **Никаких ложных возобновлений.** Отменённое вручную и завершённое задание не предлагаются; изменившийся транскрипт, промпт, модель или настройки дают `resume-mismatch` и обычный новый запуск. Двойное нажатие защищено атомарным `claimJob`, а живое задание не предлагается к продолжению даже после переоткрытия панели: второй клик получает `resume-busy` и не отправляет ни одного запроса. Использовать сохранённое задание может только первый провайдер цепочки; fallback-провайдер начинает своё задание. После завершения кнопка и плашка исчезают, `SummaryResult` собирается как обычно.
* **Бюджеты разделены по смыслу.** Один вызов — `operationBudgetMs(timeout)` = 225 с (две попытки и максимальное ожидание). Цепочка провайдеров не получает свежий бюджет на каждого: они делят абсолютный deadline задания, и переключение провайдера больше не продлевает ожидание. Single-pass — один полный вызов и один дешёвый ремонтный повтор: **370 с** вместо 460 с.
* **Map/reduce считается по волнам, а не по «всем мыслимым отказам».** Map — `(волны + 1) × 225 с` с потолком 10 минут; reduce — только те промежуточные раунды, которые реально нужны по оценке размера заметок, плюс финальная сборка с одним повтором. Итог при дефолтах: **910 с** для 3 фрагментов, **1060 с** для 11, **1285 с** для 27 (было 1360 / 2710 / 4660 с). Резерв на fallback заранее больше не вычитается: короткое видео не платит за сценарий длинного.
* **Восстановление зависит от ошибки.** `CONTEXT_LENGTH`, пришедший в первые 45 с, — определённый сигнал «не помещается»: пайплайн переходит на фрагменты и может один раз расширить deadline, но не больше 15 минут и с записью `recoveryMs` в диагностику. `TIMEOUT` такого права не имеет: молчание модели не запускает новый многоминутный сценарий, запуск завершается ошибкой. Это закреплено отдельными mock-тестами.
* **Честная подпись в панели.** Строка называется «Максимальный бюджет задания» и сопровождается пояснением, что это верхний предел на восстановление после ошибок, а не прогноз времени завершения; живой остаток по-прежнему показывается отдельно.
* **Проверено:** `npm test` — 259/259 (добавлены: возобновление только совместимого задания, кнопка «Продолжить» только при совместимом задании, отсутствие возобновления после таймаута single-pass, отсутствие повторных запросов для готовых чанков, блокировка при изменившемся транскрипте, защита от дубликата, отмена как не-возобновляемое состояние, разные пути для `CONTEXT_LENGTH` и `TIMEOUT`, общий deadline цепочки провайдеров, отсутствие новых волн и reduce после дедлайна, отмена in-flight запросов); `npm run check`; `npm run build` для Chrome и Firefox. Живых запросов к OpenRouter не было, поэтому выигрыша во времени генерации никто не заявляет: цифры выше — расчётные потолки.
* **Ограничения:** бюджет по-прежнему планируется по стратегии и настройкам, а не по измеренной скорости провайдера; расширение после `CONTEXT_LENGTH` ограничено 15 минутами и может не покрыть очень длинный транскрипт на медленной бесплатной модели; live-счётчики «в работе/ожидают» приблизительные; браузерный прогон 1.4.4 ещё не выполнялся.

## 1.4.3 — 2026-10-19 (живой замер и лечение «шести минут»)

* **Живой замер на реальном видео из репорта** (9A5mhMEmEGo, 35:12, транскрипт ~6 300 слов, снятый из ASR-дорожки): single-pass — **ровно 1 запрос, 41,6 с**, TTFT 3,0 с, генерация 38,5 с, 9 466 токенов на входе / 2 338 на выходе, `finish: stop`, модель `poolside/laguna-s-2.1:free` (роутер), JSON разобран напрямую, без повторов, repair и fallback; локальная обработка 5 мс. Конспект: 8 пунктов, 4 раздела, охват таймкодов 0:00 → 32:41 из 35:12. То есть успешный путь 35-минутного видео не занимает шесть минут — задержка сидела в путях сбоя.
* **Watchdog замирания стрима.** Новая причина: модель приняла запрос и замолчала (включая «думающие» модели, замершие между рассуждением и выводом). SSE-ридер теперь завершает попытку после 45 с тишины (`STREAM_STALL_MS` в `client.js`) вместо того, чтобы держать её до полного таймаута; каждая тишина подтверждает живость апстрима, медленный поток не обрывается. Ошибка — `TIMEOUT` с подсказкой именно про замолчавшую модель; повтор обычно попадает на рабочую модель роутера. Гонка `reader.read()` против сигнала отмены делает abort обязательным даже там, где поток не разрушается сам (SSH-подобные прокси, кастомные шлюзы).
* **Разделение «транспорт жив» и «генерация продвигается».** Keepalive-комментарии SSE (`: ping`) подтверждают только соединение и больше не могут маскировать зависшую генерацию: их касание упразднено. Теперь три раздельных окна на попытку: транспортное 45 с без единого байта (`transport-stalled`), окно прогресса 60 с без содержательных событий (текст, reasoning-дельты, finish-маркеры) после начала генерации (`progress-stalled`) и щедрое окно первого контента 150 с (`generation-not-started`) — при дефолтном таймауте 90 с оно не срабатывает и держит «думающие» модели в безопасности; окно прогресса считается только после первого содержательного события. Частичный ответ при срабатывании watchdog больше не может вернуться как «успешный» конспект; внешний cancel прекращает цикл после текущей попытки без повторов. Расчёт худших времён — в `MANUAL-TESTING.md`.
* **Единый бюджет логической операции.** Раньше повторы складывались: дефолтные `retries: 1` плюс 429-бонус могли дать 3 попытки по 90 с и два ожидания по 45 с — до 6 минут на один вызов. Теперь у `chat()` есть абсолютный deadline (`operationBudgetMs(timeoutMs)` = 2 × таймаут попытки + максимальное ожидание, по умолчанию **225 с**): первая живая генерация всегда получает полный таймаут, а повторы, 429-бонус и `Retry-After` укладываются в остаток. Если `Retry-After` не помещается в бюджет, запрос завершается сразу (`TIMEOUT`, `detail: operation-deadline`) без сна и без нового обращения к провайдеру; отмена пользователем во время паузы между попытками прекращает ожидание немедленно.
* **Единый deadline задания и fallback-цепочки.** Саммари получает абсолютный deadline (`computeJobBudgetMs`), рассчитанный по плану: стратегия, число чанков, параллелизм, лимиты вызовов, повторы/backoff, два reduce-раунда, финальная сборка и локальный резерв. Все провайдеры fallback-цепочки делят один deadline и получают только остаток; смена провайдера больше не сбрасывает бюджет. Для single-pass map-reduce-этапы не запускаются, а бюджет форсированного single — 2 × 225 + 10 с = 460 с. Map-фаза оставляет reduce не более четверти остатка, не начинает новые волны после deadline и отменяет запросы в полёте; успешные фрагменты сохраняются, неполный результат помечается `interrupted` и возобновляется без повторной оплаты готовых чанков.
* **Видимая диагностика запуска.** В панели — живая строка бюджета/остатка и стадии (включая «в работе/ожидают»), после завершения — раскрываемый отчёт: стратегия, время по этапам, запросы/повторы/переключения провайдера, последняя причина, полнота и причина завершения (`success`, `cancelled`, `call-timeout`, `job-timeout`, `provider-error`, `quota`). Всё локально, без новых запросов и телеметрии.
* **Таймаут одной попытки: 90 с вместо 180 с.**`DEFAULT_SETTINGS.ai.timeoutMs` согласован с собственным дефолтом пайплайна (комментарий там это и обещал: «90 с уже щедро, три минуты на попытку делали отказ бесконечным»). Худший случай двух тихих попыток сокращён с 6 минут до ~90 с — до этого сочетание «дефолт 180 с × retries=1» в точности воспроизводило репорт о шести минутах. ## 1.4.0 — 2026-10-19 (один запрос вместо двадцати, честная полнота)

* **Адаптивный бюджет контекста.** Решение «один запрос или фрагменты» больше не упирается в размер чанка: новая настройка `contextTokens` (128 000 по умолчанию) описывает безопасную часть окна модели, а `chunkTokens` остаётся только размером фрагмента. Транскрипт на ~64 000 токенов (3:22 видео, ~35 тыс. слов) уходит **одним** запросом вместо 20 map + 1 reduce. Промпт и схема вычитаются из бюджета отдельно.
* **Фрагменты крупнее:** 6 000 токенов вместо 3 200 — длинное видео, которое всё-таки не влезает, режется примерно на 11 частей вместо 20.
* **Полнота — инвариант.** У каждого фрагмента есть состояние (`pending / running / succeeded / retryable_failed / failed`). Пустой JSON, ответ «схемой», обрезанный по лимиту ответ и пропуск по таймауту больше не считаются успехом. Если после повторов фрагмент отсутствует, конспект помечается **неполным**: плашка «неполный охват», предупреждение с диапазонами времени, `meta.complete=false`, `stats.aiComplete=false`, и такой результат **не кэшируется**. Раньше 19 пустых ответов из 20 давали «готовый» конспект по одному фрагменту.
* **Кэш фрагментов.** Заметки map-этапа хранятся локально и переиспользуются между запусками; ключ = текст фрагмента + ревизия промпта + модель + провайдер + язык/тон/объём. Кэш ограничен 400 записями и 14 днями, очищается вместе с кэшем конспектов. Успешные фрагменты не запрашиваются повторно при сбое соседнего.
* **Диагностика.** В `SummaryResult.meta.diagnostics` пишутся стратегия, число запросов и повторов, попадания в кэш, статусы фрагментов, а по каждому вызову — TTFT, полное время, токены, `finish_reason`, фактически ответившая модель (важно для роутера `openrouter/free`) и число попыток. Без ключей, промптов и транскрипта.
* **JSON-режим** (`response_format: json_object`) включается для совместимых API: роутер бесплатных моделей учитывает это при выборе модели. Провайдер, который режим не поддерживает, получает автоматический повтор без него.
* **Исправлена плашка стратегии:** `map-reduce:degraded` и `map-reduce:partial` больше не подписываются как «одним запросом».

## 1.2.1 — 2026-10-19 (разделы не дублируются, ИИ не пересказывает схему)

### «Качество стало хуже» — три конкретные причины, все найдены и закрыты

* **Разделы повторялись три раза.** В главах видео первый маркер стоит на `0:00`, а конец главы считался как `Number(следующая) || Infinity`: ноль — ложное значение, поэтому первая глава получала конец «бесконечность» и вбирала весь трёхчасовой транскрипт. Отсюда три раздела с одним названием, одним таймкодом и одними и теми же лучшими фразами из всех трёх часов. Теперь конец главы — явная проверка `Number.isFinite`, глава без положительной длины пропускается, а повторные маркеры (`0:00` из свёрнутой и развёрнутой панели глав) схлопываются в один (`uniqueChapters`, дедуп в `getChapters`).

* **ИИ на бесплатной модели пересказывал схему.** В промпте фрагмента лежал пример `{"points":[{"text":"тезис 8-25 слов",...}],"topics":["тема"]}`, и `openrouter/free` вернул его дословно; сборка падала, а черновик показывал карточки «тема» с пунктами «тезис 8-25 слов». Пример заменён на «...», добавлено прямое запрещение копировать подписи полей, `normalizeResult` выбрасывает заглушки схемы (включая «строка: …» и «...»), а фрагмент, целиком состоящий из эха схемы, переспрашивается с напоминанием и больше не попадает в сборку как конспект.
* **«Что можно сделать» брало повествование.** Короткие подсказки (`tip`, `step`, `шаг`) искались подстрокой, и `tip` находился внутри `mul-tip-le`: «Tom tries multiple times to go down those stairs» становилось рекомендацией. Короткие подсказки теперь совпадают только с начала слова.
* **Вопросы для самопроверки.** Притяжательные формы («Johnny's») больше не считаются отдельным именем: упоминания складываются с «Johnny», слабые имена (меньше трёх упоминаний) в вопросы не попадают, максимум четыре.

## 1.2.0 — 2026-10-19 (перевод на язык пользователя, порядок как в Яндексе, скорость ИИ)

### «Должно переводить видео любого языка на язык пользователя»

* **Авто = язык интерфейса, а не видео.** Раньше режим «auto» означал «язык транскрипта», поэтому английское видео на русском интерфейсе давало английский конспект. Теперь `resolveOutputLanguage` при «auto» берёт язык UI (`uiLang`, доводится до кода из `chrome.i18n` через `uiLangFor`), а промпт требует переводить смысл, а не слова, сохраняя названия продуктов и имён.
* **Локальный движок честно предупреждает.** Без ИИ перевести нельзя — в заметках конспекта появляется строка «Локальный движок не переводит: конспект составлен на языке видео. Для перевода включите ИИ-режим.».

### «Порядок информации как в Яндексе, TL;DR отвратный»

* **Панель: сверху — связный обзор и разделы по темам.** Вкладка «Обзор» теперь строится в порядке: связный TL;DR → разделы по темам (заголовок + пересказ + 2-3 пункта) → хронологические ключевые моменты → статистика. Раньше плоский список «ключевых моментов» шёл выше смысловых разделов.
* **Экспорт согласован с панелью:** в Markdown/тексте разделы тоже идут перед ключевыми моментами.
* **TL;DR — связный пересказ всего видео.** Локальный движок берёт по одному лучшему предложению из каждой трети видео (открывающее + середина + финал), а не обрывок первой попавшейся мысли; промпты для ИИ требуют того же: «2-3 предложения по всем темам сразу, включая середину и финал».

### «С ИИ заняло почти минуту»

* **Скорость — это бесплатная reasoning-модель, а не конвейер.** Модели вида GPT-OSS тратят весь бюджет ответа на «размышления» и не доходят до JSON: помогает выбор обычной модели без режима размышления или поднятый «Максимум токенов ответа». Конвейер уже эскалирует бюджет и повторяет сборку.
* **Ограничен таймаут одного запроса** (90s) и общий дедлайн карт (10 мин): зависшая бесплатная модель больше не растягивает запуск на минуты, оставшиеся фрагменты пропускаются с предупреждением.
* **ИИ: ошибка 429 теперь ждёт, а не сдаётся.** Ответ 429 уважает заголовок retry-after и ждёт до 45 с вместо 700 мс, плюс для rate-limit даётся одна дополнительная попытка: бесплатный провайдер с лимитом «1 запрос / 30 с» больше не теряет все фрагменты разом.
* **Чанки идут параллельно.** Фрагменты независимы, поэтому в полёте держится до `Параллельные запросы` запросов (по умолчанию 6, в настройках до 20). 3,5-часовое видео — это ~15 фрагментов: при 3 запросах пять волн, при 6 — три, при 15 — одна. Провайдер, ограничивающий частоту, сам сужает окно вдвое по 429, вместо того чтобы терять весь запуск.

### Локальный движок (без ИИ) — чистка мусора

* **Санитайзер субтитров** (`cleanCaptionText`): вырезает склейки служебных строк панели YouTube («5 минут 19 секунд», «Плейлист Микс», «В эфире» и т.п.), не трогая настоящую речь с такими же словами внутри фразы.
* **Темы-прилагательные и глаголы больше не заголовки.** Улучшены эвристики ключевых слов для EN (суффиксы, inflection `s/es`, специфичность заголовков) — меньше «Model / Open / Image» вместо настоящих тем.
* **Карточки рекомендаций рядом с субтитрами больше не попадают в конспект.** Панель печатает в том же innerText «401 тыс. • 2 г. назад», «2,4 млн • 3 мес.», «В эфире», «Плейлист Микс», а чужой заголовок иногда приклеен к речи без пробела. Отсюда в конспекте были «Назадв Эфиреплейлист Микс» в ключевых словах и пункт «…and have How Israel Kills Journalists…». Теперь такие строки вырезаются целиком, а настоящая речь перед приклеенным заголовком сохраняется.
* **Чужой таймкод перед английской речью.** «17 минут involved with Israeli intelligence» — это скрытый таймкод русской панели: длительность на другом алфавите, чем продолжение фразы, считается разметкой. Внутри живой фразы числа не трогаются («5 минут назад он сказал…», «3 месяца спустя…»).
* **Скользящие авто-субтитры больше не дублируются.** YouTube отдаёт авто-субтитры окнами: каждая строка повторяет хвост предыдущей («…a lot of time» → «a lot of time digging»), и в конспекте появлялось «a lot of time a lot of time digging». Повтор снимается только у настоящего окна: строки перекрываются по времени (или идут в пределах 1,5 с), совпадает не меньше трёх слов (одно — если окна перекрываются), и это не клич, не скандирование и не повтор фразы после точки. «No, no, no» и «It was the longest day of my life. The longest day of my life, she said.» остаются как есть.
* **EN: служебные слова не ключевые.** one, people, know, former, approximately, involved, million и подобные убраны из тем и заголовков — раньше они стояли рядом с «Epstein» и «Intelligence».
* **Лид не смешивает языки.** В английском лиде союз «and», а не «и»; латиница сохраняет заглавные («About: Epstein, Israeli and Intelligence», а не «epstein, israeli и intelligence»).
* **Заголовки разделов без обрывов.** Фолбэк-заголовок режется по запятой и не кончается на «и / and / or / that…» — вместо «…, hosted former…».
* **Проверка:** тесты 184/184, `npm run check` чисто; живой прогон на реальном 40-минутном видео без ИИ даёт связный русскоязычный лид и разделы без мусорных строк.

## 1.1.0 — 2026-10-18 (правки после четвёртого репорта)

### «Без ИИ по-прежнему результат дерьмо, нихуя не понятно» — лид из описаний и разорванное начало

* **Со скриншота:** «О чём видео: мармелад и обычный. Оправившись от потерь маминых денег, наш герой складывается с одноклассником по 5000 руб. и…», ключевые слова «Мармелад, Простой, Обычный, Простой Семьи, Главная, Продает», вопросы «Что такое „Обычный“?», а заголовки разделов у всех частей одинаковые.
* **Причина 1 — прилагательные как темы.** «Обычный/простой» встречаются в репликах десятки раз и по TF-ISF обгоняют настоящий предмет видео. В `extractKeywords` добавлено определение описательных слов по их собственным словоформам (суффиксы `-ый/-ые/-ая/-ое/-ого/-ому/-ым/-ых/-ыми/-ую`; рискованные `-ой/-ий/-ие` намеренно не трогаются — «герой», «сценарий», «здание»). Описания штрафуются (×0,22 для слова, ×0,35 для фразы) и исключаются из тем, если в видео есть хотя бы три настоящих существительных. Глаголы теперь тоже не считаются темой, а не только штрафуются.
* **Причина 2 — лид начинался с обстоятельства без подлежащего.** «Оправившись от потерь маминых денег, наш герой…» отсылает к предыдущему предложению, которого в конспекте нет. Новый `stripDanglingOpener()` в `tokenize.js` снимает деепричастный оборот в начале фразы, когда он заканчивается запятой (только первое слово, только с запятой, только если остаётся самостоятельное предложение) — «Состав, который…» и «Он, оправившись…» не трогаются.
* **Причина 3 — конспект не называл героя.** Лид подбирается по предложению, которое называет человека из заголовка (или повторяющегося в транскрипте), — самым ранним из сильных кандидатов. Теперь TL;DR читается как история: «Обычный парень Гриша Соловьёв родился в простой семье. Наш герой складывается с одноклассником по 5000 руб. … В своих роликах Гриша неоднократно говорит, что привозят мармелад из Европы…».
* **Меньше повторов:** пункты больше не дублируют предложения лида (точные совпадения исключаются, близкие — штрафуются MMR), предпочитаются пункты до 30 слов, а заголовки разделов не повторяются: если темы в диапазоне нет или она уже использована, заголовком становится первый пункт части.
* **Кэш инвалидируется:** в ключ локального кэша добавлена ревизия движка (`APP.engineLocalRevision`). Без этого после перезагрузки расширения вы видели бы тот же старый конспект из кэша и правки выглядели бы неработающими.
* **Тесты:** +4 (всего 167) — снятие деепричастного оборота (с тремя защитными случаями); лид начинается с имени и не начинается с оборота; описания и единицы не попадают в темы, заголовки и вопросы; пункты не повторяют лид.

### «ИИ опять не сработал» — ответ в snake_case считался пустым

* **Причина — своя же проверка.** «Есть ли в ответе конспект» (`resultSubstance`) смотрела только на camelCase-поля (`tldr`, `keyPoints`, `sections`). Если модель вроде `openrouter/free` отвечала `summary` / `key_points` / `chapters` — а это корректный ответ, который `normalizeResult` понимает, — проверка объявляла конспект пустым, и вместо хорошего результата шёл ещё один короткий запрос, который та же модель тоже игнорировала. Отсюда «Модель не вернула конспект: ответ пустой».
* **Фикс:** проверка идёт по нормализованному объекту, единой схемой.
* **Reasoning-модели:** OpenRouter отдаёт «размышления» в поле `reasoning` (другие — в `reasoning_content`); клиент читал только второе, поэтому ответ, целиком состоящий из рассуждения с JSON внутри, выглядел пустым. Теперь читаются оба поля, и в стриминге тоже: если видимого текста нет, используется накопленное рассуждение.
* **Обрезанный ответ больше не «пустой»:** если JSON пришёл с пустыми полями из-за `finish_reason: length`, ошибка теперь `TRUNCATED` — конвейер один раз поднимает бюджет ответа до 8192 токенов вместо попытки переспросить в другом формате.
* **Уже показанный конспект больше не пропадает:** если конспект на экране уже есть (например, из кэша), неудачный ИИ-запуск не заменяет его красной карточкой, а показывает прежний результат с плашкой о причине отказа.
* **Источник:** OpenRouter docs «Reasoning Tokens» — «Reasoning tokens will appear in the `reasoning` field of each message».
* **Проверено живым запросом:** тот же конвейер (`chat` → стриминг → JSON → нормализация) прогнан на реальном OpenAI-совместимом endpoint: 17,9 с, один запрос, готовый конспект с пунктами, разделами и ключевыми словами.
* **Тесты:** +4 (всего 171) — snake_case-ответ принимается с первого запроса, без повторов; ответ, пришедший только в `reasoning` (обычный и стриминговый), читается как текст; ошибка в теле с HTTP 200 (`error: …`) становится `PROVIDER_ERROR`; уже показанный конспект сохраняется при отказе ИИ.

### Таймкод панели попадал в середину предложения

* **Со скриншота:** «1:56 · 1 минута 46 секунд последнее время он дал несколько интервью», «2:57 · 2 минуты 57 секунд Ну вы знаете…», а внутри TL;DR — «в частности, 7 минут 4 секунды супермегаэбожественный мармелад».
* **Причина:** словесный таймкод стоит в начале *каждой* строки панели, но строки склеиваются в предложение. Предыдущий фикс чистил только склеенный буфер, то есть снимал префикс лишь у первой строки, а у остальных он оставался в середине фразы. Второй пропуск: строки часто продолжают предложение со строчной буквы, а защита «настоящей речи» требовала заглавной и поэтому пропускала такой префикс.
* **Фикс:** (1) каждый сегмент чистится отдельно, до склейки (`buildSentences`); (2) словесный таймкод с секундами снимается и при продолжении со строчной буквы («1 минута 46 секунд последнее время…» → «последнее время…»), а настоящая речь с направлением времени остаётся («5 минут назад он сказал…»); (3) если строка начинается с видимого «0:08», он снимается вместе со словесной формой.
* **Тесты:** +1 и новые проверки в существующем тесте токенизатора (всего 163) — таймкод в строке-продолжении, «0:08 5 минут 19 секунд …», английский аналог («2 minutes 57 seconds the story begins» → «the story begins», «5 minutes ago…» не трогается), предложение, собранное из трёх строк, без «минут/секунд» ни в TL;DR, ни в пунктах.

### «TL;DR без ИИ отвратителен»: ключевые слова были склеены с чужими словами

* **Главная причина — баг, а не вкусовщина.** В `extractKeywords` поверхность слова бралась по индексу стема из другого массива (стемы отбрасывают стоп-слова, поэтому массивы разной длины). В итоге стем «мармелад» выводился как «что», популярные слова срывались на служебные и в ключевые слова попадали «Стоить», «Станет», «Начал», а «Мармелад» (7 упоминаний!) не попадал вовсе. Отсюда и лид «О чём видео: гриша, фирмы и начал», и заголовки разделов, и вопросы «Что такое „Стоить“?».
* **Фикс:** новый `stemPairs()` в `tokenize.js` возвращает пары «стем + его слово», `stemsOf` переписан через него; ключевые слова и биграммы строятся только по парам.
* **Меньше мусора в темах:** глагольные формы получают понижающий коэффициент (×0,45 для слов, ×0,6 для фраз), а реплики с рекламой («подпишитесь на канал», «промокод в описании») вообще не участвуют в подсчёте — раньше из-за них «Канал» становился темой видео.
* **Лид стал строже:** минимум 3 упоминания и score ≥ 0,5, единицы и валюты («руб», «процент», «тысяч») исключены, повторы вроде «кэширование, инвалидация и кэш» схлопываются по общему началу. Нет 2–3 хороших тем — лид не выводится совсем: «В своих роликах Гриша неоднократно говорит…» лучше, чем «О чём видео: простой, обычные и последнее».
* **TL;DR и пункты больше не режут фразы:** выбранные предложения ограничиваются по словам ровно на границе (32/36/30 слов, обрезка по запятой), а не по символам — «…последний день существования 9…» исчезло. Лид обрезается по предложениям, а не на середине.
* **Тесты:** +1 — лид собирается из тем, а не из единиц («руб», «процент» не проходят), и TL;DR не длиннее 70 слов.

### «С ИИ не получилось, прошло несколько минут» — вторая итерация

* **Что было:** пустой ответ модели (`finish_reason: stop`, текст «») проходил как «не-JSON», и конвейер тратил на него ещё один полный запрос на «ремонт», потом повторял всё с удвоенным бюджетом. При таймауте 180 с это и есть «несколько минут и ничего».
* **Пустой ответ теперь отдельная ошибка.** `chat()` бросает `EMPTY_RESPONSE` сразу (с `finish` и числом токенов в деталях), а `callForJson` больше не делает «ремонтный» вызов, если в ответе вообще нет «{» — на пустое нечего чинить.
* **Один компактный повтор вместо второго большого запроса.** Если ответ пустой или неразборчивый, идёт один короткий запрос: профиль «кратко», 1600 токенов ответа, без стриминга, таймаут 45 с. Помог — конспект есть; не помог — исходная ошибка и подсказка.
* **Таймаут одного запроса 180 с → 90 с.** Модель, которая не ответила за полторы минуты, не ответит и на третьей попытке.
* **Итог по времени:** в худшем случае два запроса (~2 минуты) вместо трёх-четырёх с «ремонтом», а не помогло — панель отдаёт локальный конспект (ниже).
* **Тесты:** +2 — пустой ответ даёт один компактный повтор (и ни одного «ремонтного» вызова); при повторном пустом ответе — `EMPTY_RESPONSE` с подсказкой.

### ИИ не ответил — показываем локальный конспект, а не пустой экран

* **Раньше:** после нескольких минут ожидания пользователь получал карточку «Модель не вернула конспект» и должен был сам нажимать «Сделать локально».
* **Теперь:** ошибки, означающие «модель не смогла ответить» (`EMPTY_RESULT`, `EMPTY_RESPONSE`, `BAD_JSON`, `TRUNCATED`, `TIMEOUT`, `RATE_LIMIT`, `SERVER`, `PROVIDER_ERROR`, `NETWORK`, `MAP_FAILED`), автоматически превращаются в локальный конспект (2–5 с), а над ним появляется жёлтая плашка «ИИ не справился — показан локальный конспект» с причиной, кодом и кнопками «Повторить ИИ» и «Настройки». * **Тесты:** +2 — снятие словесного таймкода в ru/en и неприкосновенность настоящей речи; конспект из транскрипта с префиксами не содержит «минут секунд» ни в TL;DR, ни в пунктах, ни в ключевых словах.

### «С ИИ не получилось»: пустой конспект больше не выглядит как готовый

* **Репорт со скриншотом:** прошло несколько минут, в панели — карточка со статистикой (`2802 слова`, `3 фрагмента`, `80 тыс → 47 тыс токенов`), предупреждения «Ответ не поместился в 2500 токенов», «JSON разобран со второй попытки», но ни TL;DR, ни пунктов: модель ответила обрезанным JSON с пустыми полями, а запуск считался успешным.
* **Бюджет ответа стал «по длине»:** схема стандартного конспекта не влезает в 2500 токенов. Потолок по умолчанию поднят до 4096, для профилей — 2048/4096/6144, а сохранённое в настройках значение ниже профиля поднимается до него (иначе ответ гарантированно обрезается); потолок повторов — 8192. Это же убирает лишний повтор: в типичном случае теперь один запрос вместо трёх.
* **Пустой результат — это ошибка, а не результат.** Если после разбора в ответе нет ни 2 пунктов, ни 2 разделов, ни 8 слов TL;DR, конвейер повторяет запрос с удвоенным бюджетом, а если и это не помогло — падает с кодом `EMPTY_RESULT` и подсказкой («попробуйте модель без режима размышления, другого провайдера или локальный движок»). Такая карточка показывает причину и действие, а не пустой «Готово».
* **В map-reduce** пустой итоговый JSON больше не выбрасывает уже собранные фрагменты: показывается черновой конспект из map-частей с предупреждением.
* **В панели** добавлен второй барьер: результат без TL;DR и пунктов не сохраняется и не рисуется — вместо него карточка ошибки с кнопками «Повторить», «Сделать локально» и «Настройки».
* **Тесты:** +3 — слишком малый бюджет поднимается и ответ приходит одним запросом; повтор при `TRUNCATED` с лимитом 8192; `EMPTY_RESULT` вместо пустого «Готово» (и карточка ошибки в панели на пустом ответе ИИ). Всего в наборе 157 тестов.

### 16-минутное видео требовало четырёх запросов к модели вместо одного

* **Репорт:** «С ИИ неприемлемо долго, больше 3–4 минут». Причина была структурной, а не в провайдере: решение «один запрос или фрагментами» принималось по **размеру чанка** (`chunkTokens`, 3200) — то есть любое видео длиннее ~10 минут речи разрезалось на части и требовало 3–4 вызова модели вместо одного.
* **Теперь у плана два разных числа:** бюджет контекста (`contextTokens`, 12000 по умолчанию) решает, влезает ли транскрипт в один запрос, а `chunkTokens` остаётся размером фрагмента для действительно длинных видео. То же 16-минутное видео становится **одним** запросом.
* **Безопасный откат:** если окно выбранной модели меньше и она ответила `CONTEXT_LENGTH`, расширение не падает, а один раз перестраивает план на фрагменты — с предупреждением в карточке.
* **Попутно пойманная ошибка:** в режиме одного запроса отправлялся `plan.chunks[0]` — только первый кусок, если транскрипт был разрезан на части. Теперь уходит весь текст; это проверяется тестом.
* **Тесты:** +2 (шестнадцатиминутный транскрипт — ровно один запрос и весь текст внутри него; решение по контексту при сохранённом размере фрагмента). Итого 151.

### Скорость и стабильность: «Merging the result» и три попытки вместо одной

* **Из журнала:** панель отдала **253 фрагмента**, но только с третьей попытки, а перед этим два раза писала `PAGE_TRANSCRIPT_NOT_SPEECH` («плотность речи 4 слов/мин, rows=11»). Причина: после переключения вкладки скрапер читал список через 250 мс, когда YouTube ещё досылал строки. Теперь `waitForRowGrowth()` ждёт, пока список перестанет расти (до 6 с, тишина 0,7 с), и только тогда считает плотность речи.
* **Первый клик больше не ошибочный:** `transcriptFromPage` сама повторяет попытку через 1,2 с, но только если первая упала быстро (до 8 с) — то есть когда панель или мост просто не успели. Медленный отказ не повторяется, чтобы не удвоить ожидание перед карточкой ошибки.
* **«Merging the result» длилось минутами:** входной бюджет сборки срезался до 70% размера чанка, и длинное видео уходило в лишние раунды иерархической сборки — каждый раунд это отдельный вызов модели. Теперь вход сборки = полный чанк (лимит ответа задаётся отдельно), а таймаут одного фрагмента ограничен 90 с — висящая бесплатная модель больше не съедает минуты на чанк.
* **Пропавшие фрагменты («модель израсходовала лимит»):** повтор для чанка сразу берёт потолок 4096 токенов вместо удвоения 1200 → 2400, и при повторах выводится понятная причина: reasoning-модели тратят бюджет на рассуждения, смените модель или поднимите «Максимум токенов ответа».
* **Прогресс с таймером:** в статусах «Анализирую N/M», «Собираю итоговый конспект» и промежуточной сборке видно прошедшее время (`3/12 · 1:47`).
* **Меньше лишних запросов:** если `get_transcript` со страницы ответил 4xx для видео, повторные попытки этого маршрута для него пропускаются.
* **Диагностика больше не врёт про провайдера:** если настройки без `ai.providerId`, панель подставляет первого доступного, но не сохраняла этот выбор — в отчёте было `active: —`, хотя запросы уходили в OpenRouter. Теперь выбор сохраняется.
* **Тесты:** +1 (повтор чанка берёт потолок бюджета и предупреждает о reasoning) и усилен тест map-фазы (прогресс обязан нести `elapsedMs`). Итого 149.

### Вкладка «Расшифровка» не находилась: искали внутри списка, а она в шапке

* **По деталям репорта:** `rows: 10/10 · timecode cells: 94 · tab=no-tab` — на экране десять пунктов глав, 94 таймкода на странице, а переключение на вкладку даже не попробовало себя: `no-tab`.
* **Причина:** вкладки искались *внутри* элемента панели, которым скрапер считал список строк. В новой разметке (`yt-section-list-renderer` → `#header` + `#contents`) шапка с вкладками — сосед списка, а не его потомок, поэтому найдено было ноль вкладок.
* **Исправление:** `findTranscriptTabs()` ищет управляющие элементы с подписью транскрипта по всей странице (`[role="tab"]`, `yt-tab-shape`, `button`, `[role="button"]`, `a`), с отсечением «длинных подписей» (иначе панель целиком считалась кнопкой). Переключение пробует до четырёх кандидатов и ждёт смены строк (2,5 с на каждого вместо 4 с).
* **Диагностика:** в журнале `tab=` теперь показывает `tried-N` — сколько вкладок нашлось, а не только факт клика.
* **Тест:** +1 — шапка `#header` с вкладками рядом с списком из десяти глав (ровно раскладка из скриншота); старый поиск в этой фикстуре находил ноль вкладок. Итого 148.

### 403 «Sorry…» на `get_transcript`: запрос теперь идёт из страницы

* **Что показал журнал:** `get_transcript` ответил `HTTP_403` с HTML `Sorry…` — это антибот-заглушка YouTube на запрос из контекста расширения (`Origin: moz-extension://…`). Тот же вызов со страницы возвращает транскрипт.
* **Мост в page-world:** новый `src/content/page-bridge.js` инжектится в страницу (web accessible resource) и делает `youtubei/v1/get_transcript` с контекстом и cookies самой страницы (`ytcfg`), `visitorData` и `getTranscriptEndpoint.params` из `ytInitialData`. Ответ уходит контент-скрипту через `postMessage`, затем в воркер на разбор (`parse-transcript`) — ES-модуль парсера контент-скрипту недоступен.
* **Порядок теперь такой:** page-API → DOM-панель → ручная вставка. Старые маршруты воркера (`timedtext`, `get_transcript`, легаси-эндпоинт) остались — они дешевле, когда не заблокированы.
* **Скрапер панели знает разметку из отчёта:** строки читаются прямо из `yt-section-list-renderer` → `yt-item-section-renderer` (точный компонент, без угадывания по таймкодам).
* **Бейдж из рекомендаций больше не убивает транскрипт:** строка `4:01:07` в 33-минутном видео раньше давала `PAGE_TRANSCRIPT_MISMATCH` и обнуляла весь результат. Теперь строки за концом видео отбрасываются, а не отклоняют скрап.
* **Откат ошибки Firefox-сборки:** `web_accessible_resources` сначала конвертировался в плоский список «для MV2», и Firefox отказался ставить расширение (`Expected object instead of "assets/icons/*"`). Firefox 128+ ждёт MV3-форму `{resources, matches}` даже в MV2-фоновом скрипте — конвертация убрана, а сборка теперь проверяет, что каждый файл из `web_accessible_resources` существует в `dist/`.
* **Тесты:** +2 (панель, отрисованная как `yt-section-list-renderer`/`yt-item-section-renderer`, с бейджем в 4 часа; разбор ответа `get_transcript` от моста и кодированная ошибка на HTML-заглушку). Итого 147.

### Отчёт «пустой журнал» и кнопка «Повторить», которая ничего не делала

* **Репорт:** диагностика с Firefox 140 показала `transcript log (last 20, oldest first): — empty` сразу после явной ошибки `POT_REQUIRED`. То есть журнал молчал ровно тогда, когда он и нужен.
* **Причина 1 — вечный кэш в странице настроек:** `loadJournal()` читал хранилище один раз за жизнь страницы, а блок диагностики обновлялся только при загрузке. Окно настроек, открытое до сбоя, так и оставалось с пустым списком. Теперь чтение всегда идёт в хранилище, а кнопка «Скопировать диагностику» сначала перечитывает журнал.
* **Причина 2 — запись могла не успеть:** `recordJournal` писал в `storage.session` без ожидания, а воркер завершается сразу после ответа. Теперь запись идёт и в `session`, и в `local` (фолбэк для сборок без `storage.session`), а `flushJournal()` дожидается её до отправки ответа.
* **Причина 3 — кнопка «Взять транскрипт со страницы» блокировала панель:** при ошибке флаг `running` не сбрасывался, и все последующие «Повторить» выходили из `run()` на первой строке — без запроса и без сообщения. Теперь сброс в `finally`.
* **Новый маршрут для PO-token видео:** легаси-эндпоинт `video.google.com/timedtext` — он живёт вне PO-token конвейера плеера и отдаёт текст там, где `/api/timedtext` возвращает пустое тело и `get_transcript` отказывает. Пробуются языки дорожек (`manual`, затем `asr`); каждый ответ виден в журнале как `legacy-timedtext`.
* **Причина отказа сервера в журнале:** `get_transcript` теперь пишет не только HTTP-код, но и текст ошибки YouTube (`Precondition check failed`, `This video is unavailable`, статус `playabilityStatus`) — без этого следующий отчёт снова был бы неотличим от «опять не работает».
* **Тесты:** +4 (легаси-эндпоинт: URL и разбор XML, пустое тело и 404; спасение PO-token видео через легаси-путь в воркере; запись в хранилище до ответа). Итого 145.

### Скрапер читал один блок строк из всей панели

* **Репорт:** карточка «Something went wrong · POT_REQUIRED» с деталями `panel: true · rows: 8/8 · timecode cells: 172 · duration: 2197s` — панель открыта, таймкод-ячеек на экране 172, а строк прочитано восемь. Причина: строки группировались по ближайшему контейнеру с несколькими таймкодами, а YouTube вкладывает строки в блоки виртуализации — побеждал один блок из восьми строк, и часовое видео выглядело полутораминутным.
* Строка теперь определяется от своего таймкода: берётся самый крупный предок, в котором этот таймкод единственный (обёртки над ним держат много строк), а контейнер для прокрутки — ближайший общий предок всех принятых строк. Регрессионный тест: 24 строки в трёх блоках по 8 читаются целиком, а не первые 8.
* **Вкладка «Эпизоды»:** у панели «В этом видео» две вкладки, и главы тоже состоят из таймкодов. Если прочитанное не проходит проверки (меньше трёх строк, таймкоды за длительностью видео, меньше 20 слов в минуту), расширение один раз переключает панель на вкладку с транскриптом и перечитывает её — событие `PAGE_TRANSCRIPT_TAB` видно в журнале. Подсказка в карточке ошибки теперь просит проверить выбранную вкладку.
* Тесты: +2 (все блоки виртуализации; переключение «Эпизоды» → «Расшифровка видео»). Итого 141.

### Журнал транскрипта в диагностике

* Последние **20** событий транскрипта — какой путь пробовался, что ответил, с каким кодом и почему не вышло — пишутся в кольцевой буфер (`src/common/journal.js`) и в `chrome.storage.session`, поэтому история переживает перезапуск service worker'а. Страница настроек вставляет их в блок «Скопировать диагностику»: `OK` / `WARN` / `FAIL`, время, маршрут, код, счётчики.

Текста страницы и секретов в журнале нет — только коды, счётчики, идентификатор видео и хост.

### Транскрипт через тот же API, что у панели «Расшифровка видео»

* **Главное:** транскрипт больше не зависит от PO-token и от разметки. `ytInitialData` содержат `getTranscriptEndpoint.params` — ключ, который панель отправляет в `youtubei/v1/get_transcript`. Этим путём конспект строится, даже когда `/api/timedtext` отвечает пустым телом, а DOM-скрапер бессилен. Порядок теперь такой: timedtext → `get_transcript` → чтение панели на странице.
* Запросы идут только на `youtube.com` и с учётными данными текущей сессии — как и раньше с субтитрами; новых серверов нет.
* Для запроса теперь берутся **клиентская версия и visitorData со самой страницы** (`INNERTUBE_CONTEXT_CLIENT_VERSION`, `visitorData`). С зашитым годовалым номером версии endpoint отвечает отказом — это самая вероятная причина, почему фолбэк не срабатывал.
* **Диагностика в карточке ошибки:** если все три пути не сработали, в «Деталях» рядом с `code` теперь выводятся счётчики скрапера (`panel`, `rows/rowsUnfiltered`, `timecode cells`, `duration`), а не только код.
* Тесты: +3 на новый путь — разбор обоих форматов `get_transcript`, сквозной сценарий «все дорожки защищены → текст из API, timedtext не вызывается» и тот же сценарий через **воркерный** `loadTranscript` (именно его вызывает расширение), с проверкой источника `captions-ui`, определённого языка и отсутствия запросов к timedtext. Итого 135.

### Панель транскрипта читается без привязки к разметке YouTube

* Новый интерфейс YouTube («В этом видео» → «Расшифровка видео») не использует знакомые компоненты: таймкод — отдельный элемент-плашка, строки — анонимные `div`, имя класса зависит от эксперимента. Прежний поиск по `ytd-transcript-renderer` на такой панели находил пустоту, и расширение сообщало «Панель не нашлась», хотя транскрипт был на экране. Теперь строки восстанавливаются по самим таймкодам: для каждого элемента-таймкода берётся ближайший контейнер, в котором этот таймкод единственный (карта счётчиков вместо `innerText` по всем предкам — иначе на большой странице это лишний layout), и группируются по общему родителю; побеждает группа с наибольшим числом строк.
* Список транскрипта виртуализирован: в DOM живут только видимые ~10 строк. Раньше читалось ровно то, что видно, и конспект часового видео строился по полутора минутам. Теперь панель прокручивается шагами по 1,4 экрана (бюджет 25 с), строки собираются в множество, после чего список возвращается на прежнюю позицию.
* Панель глав («Эпизоды») больше не может выдать себя за транскрипт: группы внутри `macro-markers`/`chapter`-контейнеров отклоняются, а заголовки панели, кнопки и поисковая строка (`В этом видео`, `Эпизоды`, `Поиск в расшифровке`…) не попадают в сегменты.
* Текстовая резервная ветка (когда строк нет вообще) склеивает перенесённые строки одного сегмента и понимает оба расклада: `0:12 текст` и таймкод отдельной строкой. Вставка текста вручную тем же разбором сохраняет таймкоды — раньше двухстрочная копия панели считалась «текстом без времени» и метки терялись.
* Язык транскрипта определяется по самому тексту (кириллица/латиница) вместо `auto` — подсказки, промпты и язык конспекта больше не зависят от настройки «Авто».
* Мелочи того же пути: кнопка «показать транскрипт» ищется и среди вкладок (`[role="tab"]`), ссылки (`a`) больше не кликаются (случайный переход по странице), развёрнутое описание не сворачивается повторно, кнопка закрытия панели ищется по `aria-label` на любом языке, найденный транскрипт кэшируется на 5 минут, а тосты и надписи панели переведены (`Вставить текст`, `Показать ещё N`, `фильтр`, результат вставки).
* `npm run build` больше не падает из-за заблокированного ZIP: при `UNKNOWN`/`EPERM`/`EBUSY` архив удаляется и записывается заново (в Windows его держит просмотрщик архивов или антивирус).
* **В конспект попадали названия рекомендованных видео.** У каждого ролика в правой колонке есть бейдж длительности (`1:14:51`) — это точно такой же элемент-таймкод, как в панели расшифровки. Список рекомендаций давал «четыре строки с одним родителем», расширение считало, что панель уже открыта, и конспектировало заголовки чужих видео («назадВ эфиреПлейлист Микс… 7,4 тыс. • 10 мес.»). Теперь поддеревья миниатюр/карточек/плеера/комментариев/шортсов отбрасываются до группировки, а найденный транскрипт сверяется с длительностью видео: таймкод за её пределом означает, что прочитано не то — панель честно сообщает «панель не нашлась» вместо бреда.
* Если строк заметно меньше, чем должно быть у видео такой длины (`длительность / 20`), дополнительно читается текст панели и берётся более полный результат — так виртуализированный список не обрезается до первого экрана.
* Финальная проверка «на речь»: меньше 20 слов в минуту — это не транскрипт (репорт давал 157 слов на 24:40), такой результат отклоняется вместо отправки в модель; в консоль пишется диагностика.
* **Регрессия того же дня, исправлена:** первый вариант фильтра исключал всю колонку `#secondary-inner` — а панель расшифровки часто докидывается именно туда, поэтому после фильтрации рекомендаций пропала и панель («снова панель не найдена»). Теперь исключаются только карточки (миниатюры/локи), сама колонка — нет; если строк не нашлось, фильтр ослабляется и решение принимают проверки длительности и плотности речи. Новый тест: панель, вложенная в `#secondary-inner` рядом с рекомендациями, читается.
* **Повторный клик по кнопке в описании больше не закрывает открытую панель:** если в DOM уже есть панель, расширение только ждёт строки и переключает вкладки внутри неё, а не жмёт страничный тумблер.
* Таймкод-плашка распознаётся и с обрамлением («48:17 •», «— 48:21»), но заголовок главы («0:00 Вступление») плашкой не считается — иначе список глав снова стал бы «транскриптом».
* **Диагностика вместо «опять не работает»:** в блоке «Детали» ошибки теперь видно, что именно нашёл скрапер (панель есть/нет, сколько строк с фильтром и без, сколько таймкод-ячеек, длительность видео), а причина отказа пишется в консоль — по такой строке можно точно понять, новый ли это вид разметки.
* Тесты: +11 конца-в-конец на «панель нового вида» (строки без имён компонентов, бейджи длительности рекомендованных видео рядом с панелью и без неё, отсев таймкодов за длительностью видео, таймкод с пунктуацией против заголовка главы, отказ от списка глав, склейка переносов, вставка двухстрочной панели) и минимальный движок селекторов в стаб-DOM, чтобы контент-скрипты проверялись на настоящем дереве. ### Субтитры, защищённые PO-token

* YouTube помечает дорожку субтитров части видео параметром `exp=xpe`: на запросы вне плеера такой адрес отвечает HTTP 200 с **пустым телом**, и раньше это выглядело как тупик «Дорожка субтитров пуста». Теперь такие дорожки распознаются сразу (код `POT_REQUIRED`), лишние запросы не делаются, а панель предлагает действия: «Взять транскрипт со страницы», «Показать транскрипт на YouTube», «Вставить текст вручную».
* Панель «Транскрипт» на странице ищется по названию кнопки на **любом языке интерфейса** (было только `transcript` / «Транскрипт», поэтому русская кнопка «Показать текст видео» не находилась): теперь учитываются варианты ru/en/es/de/fr/pt/it/nl/uk/ja/zh/ko, разворачивается описание видео и проверяется меню «…». Сегменты читаются и из новых компонентов YouTube (`yt-transcript-segment-renderer`, `transcript-segment-view-model`).
* Если все веб-дорожки защищены PO-token, расширение запрашивает дорожки у приложений-клиентов InnerTube (ANDROID/IOS) — они часто отдают обычные ссылки timedtext, и конспект строится как обычно.
* Даже если разметка панели неизвестна, текст разбирается по таймкодам прямо из контейнера панели — резервный путь без зависимости от имён компонентов YouTube.
* Подсказки в карточке ошибки больше не смешивают языки: текст из воркера (всегда русский) больше не приклеивается к подсказке панели, а про неудачу фолбэка сообщается отдельной строкой — раньше можно было получить русское сообщение с английским хвостом.

### ИИ-ответы

* Обрезанный ответ модели больше не тупик: при `finish_reason = length` (и `CONTEXT_LENGTH`) запрос один раз повторяется с удвоенным лимитом вывода (до 4096 токенов), в map-reduce так же повторяются отдельные фрагменты. Если повтор не помог, показывается исходная ошибка с понятной причиной («модель израсходовала лимит, обычно так ведут себя думающие модели»).
* У OpenRouter в пресете по умолчанию теперь `openrouter/free` — встроенный роутер по бесплатным моделям, который не устаревает.
* В панели рядом со списком моделей появилась кнопка ⟳: список моделей подтягивается напрямую с API провайдера, без похода в настройки.

### Исправлено

* **Кнопка на странице исчезала без панели.** Во встроенном режиме панель попадала в колонку YouTube с `contain: layout` на контейнере, из-за чего её `position: fixed` считалась от блока нулевой высоты и панель рендерилась высотой 2 px. Теперь встроенная панель — обычный блок в колонке (`.osum-root[data-docked="true"]`), а после закрытия контейнер возвращается на страницу вместе с плавающей кнопкой.
* Панель не открывалась, если фон не успевал ответить (холодный запуск event page в Firefox): `open()` больше не падает молча — панель показывается, а причина выводится тостом.
* При навигации по YouTube колонка пересоздаётся: открытая панель переприкрепляется к новой разметке, а не остаётся вне DOM.

## 1.0.0 — первая публичная версия

### Движки конспектирования

* **Локальный (без ИИ)** — полностью офлайн: предложения с таймкодами, TF-ISF + TextRank + MMR, разделы через TextTiling, ключевые слова (уни- и биграммы), лексиконная тональность, карта плотности, BM25-поиск по транскрипту для Q&A. 900 предложений ≈ 0.2 с.
* **ИИ-режим** — единая схема результата с локальным режимом. Стратегии `single` и `map-reduce` (с иерархическим объединением частей), стриминг ответа, отмена, повторы с backoff, JSON-ремонт ответа модели, деградация до частичного результата, ограничение контекста для Q&A.

### Провайдеры

* Четыре семейства API в одном клиенте: OpenAI-совместимый, Google Gemini, Anthropic Messages, Ollama.
* ~35 пресетов, включая бесплатные тарифы (Google AI Studio, Groq, Cerebras, OpenRouter `:free`, Mistral, GitHub Models, SambaNova, Together, Cloudflare Workers AI, NVIDIA NIM, Qwen, Zhipu, Moonshot, SiliconFlow, Chutes, Hyperbolic, ArliAI) и локальные (Ollama, LM Studio, llama.cpp, vLLM, Jan, text-generation-webui).
* Загрузка списка моделей и проверка связи прямо из настроек, автопереключение на резервного провайдера, учёт расхода (запросы, ошибки, токены).

### Интерфейс

* Панель на странице видео в Shadow DOM: встроенная в колонку YouTube или поверх страницы; вкладки «Обзор», «Разделы», «Таймлайн», «Вопросы», «Транскрипт».
* Кликабельные таймкоды, гистограмма важности, поиск по транскрипту с подсветкой и синхронизацией с плеером, ручная вставка текста.
* Popup с быстрыми действиями, popup-история, горячие клавиши (`Alt+Shift+S`, `Alt+Shift+D`), контекстное меню по ссылке на видео.

### Технически

* `strict_min_version` для Firefox поднят до 128.0 — раньше сборка заявляла несовместимую версию для модульного фона.
